## 1. modernc.org/sqlite driver symbol — ANSWERED

`Driver` is an exported struct. Registration is one line:

```go
func init() { sql.Register("sqlite3", &sqlite.Driver{}) }
```

`modernc.org/sqlite` also exports `NewConnector(dsn string) (driver.Connector, error)` if a
connector is ever needed instead.

**Change to Task 4:** the plan's `sqlited` package does **not** need a custom `Open` method to
force `PRAGMA foreign_keys`. The DSN handles it (finding 2). Drop the wrapper type; register
`&sqlite.Driver{}` directly.

## 2. DSN pragma syntax — ANSWERED

This exact form works, verified by reading the pragmas back:

```text
file:<path>?_pragma=journal_mode%28WAL%29&_pragma=busy_timeout%285000%29&_pragma=foreign_keys%28ON%29
```

Built with `url.Values` and three `Add("_pragma", ...)` calls, exactly as the plan's
`FileDSN` does. Read back after `Ping`:

| Pragma | Value |
|---|---|
| `journal_mode` | `wal` |
| `busy_timeout` | `5000` |
| `foreign_keys` | `1` |

**Bonus:** `CREATE VIRTUAL TABLE t USING fts5(...)` succeeds — FTS5 is compiled in, so M7
search needs no additional dependency. Confirms spec decision D4.

## 3. Does keyring reintroduce cgo? — ANSWERED, and it is more subtle than the plan assumed

**Building is fine.** With `CGO_ENABLED=0`, `keyring` + `modernc.org/sqlite` compile cleanly for
all four targets:

| Target | Result |
|---|---|
| `darwin/arm64` | OK |
| `linux/arm64` (the NAS) | OK |
| `linux/amd64` | OK |
| `windows/amd64` | OK |

**But the macOS Keychain backend is cgo-gated and vanishes silently:**

```text
CGO_ENABLED=0   available backends: [pass file]
CGO_ENABLED=1   available backends: [keychain pass file]
```

The build does not fail. `keyring.Open` does not fail. The token simply lands in an encrypted
file instead of the macOS Keychain, with no diagnostic. This is the same
non-deterministic-backend hazard the spec warned about (§7), arriving through a different door
than expected.

**Changes to Task 10:**

1. Build matrix is now explicit: **macOS dev builds use `CGO_ENABLED=1`** to get Keychain;
   **cross-compiled Linux release builds use `CGO_ENABLED=0`** and get secret-service or file.
   This costs nothing — `modernc.org/sqlite` is pure Go either way, so CGO being on for a mac
   build does not make the mac binary cgo-dependent for SQLite.
2. `NewKeyring` must **report which backend it selected** rather than silently accepting a
   fallback. A user who believes their refresh token is in the Keychain when it is in a
   passphrase-protected file has been misled about their own security posture.
3. The plan's Task 10 Step 6 check (`CGO_ENABLED=0 ... go build ./...` succeeds) is necessary
   but **not sufficient** — it passes here and would not have caught this. Add an assertion on
   `keyring.AvailableBackends()` per platform.

## 4. Do stored and appended bytes hash-match? — **YES**

Run against a real 19,033-message mailbox on 2026-09-08:

```text
stored   732db3007da764ae61f008c50348ca421c0b6b3c7f03fd34edadb6061c0a0d35  (12,309 bytes)
restored 732db3007da764ae61f008c50348ca421c0b6b3c7f03fd34edadb6061c0a0d35  (12,309 bytes)
```

`FETCH BODY.PEEK[]` → sha256 → `APPEND` → `FETCH` again produces identical bytes and
identical length. The acceptance criterion in the spec stands as written: byte equality,
not a normalised comparison.

**This is the product's central claim, and it is now evidence rather than assumption.**

## 5. Throughput — bandwidth is not the binding constraint

| | |
|---|---|
| Sample message | 12,309 bytes, fetched in 0.37 s |
| Mailbox | 19,033 messages ≈ **223 MB** |
| Against the 2,500 MB/day cap | **9%** — one day's allowance covers eleven such mailboxes |
| Sequential fetch time | ~2.0 h |

The 0.37 s is round-trip latency, not transfer time: 12 KB does not take a third of a second
to move. **The bottleneck is per-message round trips, not bandwidth**, which inverts the
concern recorded in the spec. M2 should pipeline and batch FETCH rather than throttle on
bytes. Bandwidth only binds for mailboxes above roughly 2 GB.

## 6. Does `APPEND` rewrite headers? — **NO**

Byte-identical, so no rewriting occurred. Note this was a plain message; a spam-classified
or DKIM-failing message may behave differently and is worth re-testing at M4.

## 7. `CONDSTORE` after authentication — **NO**

```text
X-GM-EXT-1   yes
CONDSTORE    no
QRESYNC      no
UIDPLUS      no
MOVE         no
```

Gmail does not advertise `CONDSTORE` before **or** after login. There is no cheap
MODSEQ-based incremental sync. **This changes M3**: incremental sync must fetch UIDs above
the stored `UIDNEXT`, and detect flag, label and deletion changes by periodic reconciliation
over the UID range rather than by asking "what changed since MODSEQ *n*". That is more
expensive, and it makes reconciliation mandatory rather than a safety net — which is what
handoff §30 argued for anyway.

**`UIDPLUS` is not advertised, yet `APPEND` returned `[APPENDUID 12 61611]`.** Gmail supplies
the response code without claiming the capability. Useful — restore learns the new UID
directly — but it must be treated as a best-effort optimisation with a fallback, since an
undeclared capability can be withdrawn without notice.

## 8. Gmail extensions — **all present**

```text
19033 (X-GM-THRID 1875713684672698126 X-GM-MSGID 1875713684672698126
       X-GM-LABELS ("\\Inbox") UID 61610)
```

`X-GM-MSGID`, `X-GM-THRID` and `X-GM-LABELS` all return as documented. Labels arrive as a
list of quoted atoms with system labels backslash-prefixed.

## 9. Is the API message id the hex form of `X-GM-MSGID`? — **shape confirmed, not cross-checked**

```text
X-GM-MSGID decimal: 1875713684672698126
as hex:             1a07dfa88341570e
```

Sixteen hex characters, which is the shape of a Gmail API message id. **Not yet verified
against the API itself**, which would need the Cloud project this pivot avoided. Until it is,
the two-connector compatibility claim in spec §6 is plausible, not proven. `external_id` is
normalised to the hex form regardless, so being wrong costs a migration rather than a redesign.

## 10. Raw `X-GM-*` fetch items from Go

Confirmed via raw IMAP. `emersion/go-imap/v2@beta.8` has no `X-GM` support, so M1 must
either use the library's raw-command escape hatch or issue these fetch items directly.

## Checkpoint shape

```text
"[Gmail]/All Mail" (UIDNEXT 61611 UIDVALIDITY 12)
```

`UIDVALIDITY` + `UIDNEXT` is the checkpoint, exactly as spec §6 assumed.

## Superseded question list

The connector is IMAP rather than the Gmail API (spec §6, D12), so these need an app password
on a throwaway Gmail account with 2FA enabled — not a Google Cloud project.

- **4. Do stored and appended bytes hash-match?** The thesis.
- **5. Observed FETCH throughput**, and where the 2,500 MB/day cap bites. IMAP is
  bandwidth-bound, so record MB/minute and average message size.
- **6. Does `APPEND` store the bytes unmodified,** or does Gmail rewrite headers?
- **7. Does Gmail advertise `CONDSTORE` after authentication?** It does not before —
  verified against `imap.gmail.com` on 2026-09-08. Without it, M3 falls back to `UIDNEXT`
  scanning.
- **8. Do `X-GM-MSGID` / `X-GM-THRID` / `X-GM-LABELS` behave as documented** on a real mailbox?
- **9. Is the API message id the hex form of `X-GM-MSGID`?** The two-connector plan (spec §6)
  depends on both transports producing the same `external_id`. If they differ, switching
  transports means re-ingesting the mailbox.
- **10. Can a Go IMAP client issue raw `X-GM-*` fetch items?** `emersion/go-imap/v2@beta.8`
  has no `X-GM` support — verified by inspecting the module — so this is needed either way.
